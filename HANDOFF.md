## Platform: Siteforce (Salesforce Experience Cloud)

Confirmed via HAR capture: **all** traffic is a single RPC endpoint, no separate REST/Connect API in use.

- Endpoint: `POST /s/sfsites/aura?r=N&aura.ApexAction.execute=1` (r= is just a request counter, ignore).
- Request `message` param (URL-encoded JSON): `{"actions":[{"id":"...","descriptor":"apex://Controller/ACTION$method","params":{...}}]}`
- Response JSON: `{"actions":[{"id":"...","state":"SUCCESS","returnValue":{...}}]}` — match by `id`.
- Auth context: `aura.context` (fwuid, app config) + `aura.token` (CSRF-ish, session-bound) — both scraped from page's initial HTML bootstrap script (`window.Aura.appBootstrap` / `Aura.Bootstrap.bootstrap(...)`). Token expires — re-scrape on `INVALID_TOKEN`/reload.
- Checked for `/services/data/...` (standard Salesforce REST/Connect API) — 404/not present on this domain. Portal doesn't expose it. **Don't bother with OAuth/REST route, stick to aura.**

## Mobile app

**Confirmed 2026-09-01** via Chrome remote debugging (`chrome://inspect`, USB debugging): `com.myflame` is a **React Native app wrapping a `react-native-webview`** pointed at `https://my.flame.edu.in/s/` — NOT Salesforce Mobile Publisher, not a plain native WebView wrapper as originally guessed. Evidence: `libhermes.so`, `libreactnative.so`, `libfbjni.so`, `librnscreens.so` in the APK; logcat shows `RNCWebViewManager`/`RNCWebViewClient` (the standard `react-native-webview` library's Android classes); `assets/index.android.bundle` is precompiled **Hermes bytecode** (magic `C6 1F BC 03`), not readable/patchable plain JS. App is a split-APK install (base + `arm64_v8a`/`en`/`xxhdpi` config splits) — the arch split alone carries the whole React Native native runtime, so any repackage must merge all splits, not just `base.apk`.

Since it's ultimately still a real `android.webkit.WebView` under the hood (RN just creates one via its own Java classes), the same Frida-gadget-hooks-WebView approach outlined below applies regardless of the RN wrapper — RN doesn't block it, it just means the hookable class name (`RNCWebViewClient` or similar) has to be discovered at runtime rather than assumed, and console output/behavior needs testing on the actual app rather than assumed from a generic "webview wrapper" mental model.

**iOS**: sideload resigned IPA via AltStore/Sideloadly + personal Apple ID, no jailbreak needed for a simple config/JS patch. Real runtime hooking (Frida-equivalent) without jailbreak is not really viable — skip if it comes to that, not worth the effort for this project. Not attempted yet.

### Android APK patch attempt (2026-09-01) — tooling built, injection unresolved

Goal: inject `portal-reskin.user.js` into the app's WebView automatically on every launch, no computer needed at runtime (Frida Gadget in **autostart "script" mode**, not a live `frida -U` attach session).

**Environment set up** (all in `.patch-tools/`, gitignore-worthy, not committed):
- `jdk-openjdk` + `android-apktool` (AUR) installed via pacman/yay (needed the user's sudo password, run manually).
- `.patch-tools/venv/` — Python venv with `objection` + `frida-tools` (`pip install objection frida-tools`), avoids needing sudo for the Python side.
- `.patch-tools/build-tools/` — extracted `build-tools_r34-linux.zip` (direct-download, no `sdkmanager`/license flow needed) purely for the classic `aapt`, `apksigner`, `zipalign` binaries — **`objection patchapk` needs real `aapt` specifically** (not `aapt2`) to run `aapt dump badging` and find the launchable Activity; this is separate from and unconditional on apktool's own `--skip-resources` flag, which only skips apktool's *own* resource decompilation step. apktool 3.0.2 (pacman/AUR) bundles its own `aapt2` internally and doesn't need a system `aapt` at all — only objection's separate check does.
- `.patch-tools/APKEditor.jar` (REAndroid/APKEditor, direct GitHub release download) — merges the 4 split APKs into one monolithic APK (`apkeditor m -i <dir> -o merged.apk`) before patching, since `react-native-webview`'s native libs live in the arch split, not base.
- `.patch-tools/hook.js` — the Frida script (generated by a small inline Python snippet from `portal-reskin.user.js`, embedding it as a JSON-escaped string constant; **do not hand-edit** `hook.js` directly, regenerate it from the generator snippet in this session's history if the userscript changes).
- `.patch-tools/gadget-config.json` — `{"interaction": {"type": "script", "path": "libfrida-gadget.script.so"}}`, per `objection patchapk --help`'s documented convention for autostart mode.

**Patch command that worked** (after the bugs below were fixed):
```
export PATH="$PWD/build-tools/android-14:$PWD/venv/bin:$PATH"
export JAVA_TOOL_OPTIONS="-Xmx6g"
objection patchapk -s flame-merged.apk -a arm64-v8a -c gadget-config.json -l hook.js -j 1
```

**Bugs found and fixed along the way** (all confirmed against real behavior, not guessed):
1. **`-a arm64` vs `-a arm64-v8a`** — passing the short `arm64` form makes objection name the native-lib folder literally `lib/arm64/` instead of Android's real ABI folder name `lib/arm64-v8a/`. The linker only searches real ABI names, so the gadget `.so` silently isn't found (`UnsatisfiedLinkError: dlopen failed: library "libfrida-gadget.so" not found`) even though the file is genuinely present in the APK. Fix: always pass the *exact* string `adb shell getprop ro.product.cpu.abi` returns.
2. **`OutOfMemoryError` during apktool's smali rebuild** — default JVM heap too small for this app's large multidex/RN smali tree. One rebuild thread died silently mid-build while the overall process still reported "success" and continued to zipalign/sign a **corrupted APK**. Fix: `JAVA_TOOL_OPTIONS=-Xmx6g` + `-j 1` (single-threaded rebuild, avoids parallel peak-memory pressure). This one is dangerous precisely because objection doesn't hard-fail on it — always check for `OutOfMemoryError` in the "may have failed, read the output" sections objection prints, don't just check the exit code.
3. **`Java.use('android.webkit.WebView')` crashes Frida's Java bridge** (`access violation accessing 0x0`, native crash inside `/frida/bridges/java.js`) **if called too early** — confirmed via live `frida -U -l script.js -n <process>` testing. Root cause: the real `android.webkit.WebView` implementation is loaded from a separate WebView-provider classloader (Chromium/Trichrome package) that may not exist in the process's classloader list yet at script-start; Frida's classloader search picks up an incomplete stub. Fix confirmed by direct test: wrap the `Java.use('android.webkit.WebView')` call in a try/catch + `setTimeout(retry, 1000)` loop — succeeds cleanly once the app has had a moment to actually create a WebView. **This fix is in the current `hook.js`.**
4. **Frida spawn mode (`frida -U -f <pkg>`) doesn't work on this non-rooted device** — `Failed to spawn: need Gadget to attach on jailed Android`. Expected: spawn-and-inject needs root (frida-server) or an already-embedded gadget; on a jailed device you can only **attach** (`-n <process-name>`) to something already running, which inherently races against however early the app calls `setWebViewClient` (usually before an external attach can happen). This is fine for the *autostart* production config (the gadget script runs from `System.loadLibrary` time, effectively before the app does anything), but it means **live `frida -U -n` attach can't be used to test the "catch the very first setWebViewClient call" behavior** — only the autostart config's own real timing can.

**Where it stands, unresolved**: with the ABI-folder fix + OOM fix + classloader-retry fix all applied, the gadget `.so` loads cleanly (confirmed via `adb logcat`, no `UnsatisfiedLinkError`), the app runs normally, real navigation reaches `https://my.flame.edu.in/s/` (confirmed via `ReactNativeJS` log lines showing the SSO `frontdoor.jsp` redirect completing) — **but the reskin never visually appears** (screenshotted the stock Siteforce UI, unmodified). No `[flame-inject]` log lines appear either, but that's inconclusive on its own: a gadget in `"type": "script"` autostart mode has no attached Frida client to receive `console.log` messages, and this Frida version doesn't appear to fall back to Android logcat for that mode (confirmed indirectly: switching to the same gadget in plain listen-mode + live `frida -U -n` attach *does* show `console.log` output fine, in the terminal, not logcat — so logcat silence in autostart mode isn't proof of failure by itself).

**Diagnosis was in progress, not concluded**, when this was parked: the plan was to reinstall the plain listen-mode diagnostic build, live-attach with a minimal probe script (`Java.choose('android.webkit.WebView', {...})` to find the real instance directly and call `evaluateJavascript` by hand), and confirm whether `evaluateJavascript` itself works via Frida's Java bridge on this specific device/app/WebView-sandboxing setup at all, before assuming the fault is in the hook's `setWebViewClient` override logic specifically. That probe was written (`.patch-tools/probe.js`) but not run to completion — session moved to a simpler fallback instead. **Resume from here next time**, tools are all still set up in `.patch-tools/`.

Our hook hooks whatever class `setWebViewClient` is actually called with (dynamic, not hardcoded), so this shouldn't matter, but hasn't been directly confirmed by inspecting the live instance's class name.

## Tooling built
`parse_aura_har.py` (scratchpad — **move this into the new project folder**):
- Input: exported HAR file.
- Parses every aura `ApexAction.execute` POST, matches request `actions[]` to response `actions[]` by id, dedupes by descriptor+params signature, groups by page (via HAR page refs).
- Output: `<prefix>.json` (full data) + `<prefix>.md` (readable, per-descriptor sections with params + returnValue samples).
- Usage: `python3 parse_aura_har.py portal.har booking_map`

## Android patch — session 2026-09-01 (afternoon): live attach fully confirmed working, autostart still unresolved

Resumed exactly where the previous session parked (`.patch-tools/probe.js`). Findings, in order:

- **`evaluateJavascript` fully works on this device/app** — visually confirmed (probe set `document.body.style.background='red'`, screenshotted red bars at the page edges through the actual post-login portal WebView). Not blocked by CSP, sandboxing, or the Frida Java bridge.
- **Root cause of probe's first "silent failure"**: `Java.choose('android.webkit.WebView', ...)` found zero instances because the app shows a **native React Native login screen first** (Google/MyFLAME-credentials buttons) — the WebView doesn't exist until *after* sign-in navigates to the portal. - **`hook.js`'s actual hook logic is correct and works end-to-end under live attach.** Force-stopped the app, relaunched, and raced a live `frida -U -n MyFLAME -l hook.js` attach against it (scripted back-to-back in one shell command to remove human latency). Full log sequence observed:

### Root cause chain (each layer was real and had to be found in order)
1. Gadget `type:"script"` (autostart) mode's raw JS execution context has **no ambient `Java` global** and **no npm-style module resolution** on a bare, unbundled script file. The interactive `frida` CLI (used for every earlier "it works!" live-attach test) auto-bundles/polyfills `Java` for convenience — that convenience is exactly what was masking this for the entire first half of the session. A script handed directly to `objection patchapk -l <file>` gets none of that; it's just raw text dropped into the gadget's script slot.
2. Diagnosed via **`__android_log_print`-based logging that bypasses the Java bridge entirely** (`liblog.so`'s native export via `NativeFunction`, tag `FlameInjectNative`) — this was essential because the moment `console.log`/`android.util.Log` depends on `Java.*` being usable, a broken Java bridge silences your diagnostic along with the thing it's diagnosing. This is the key technique to reuse if any future gadget script-mode issue comes up: **always instrument with a Java-bridge-independent native log first.**
3. Fix attempt 1, `require('frida-java-bridge')` as a bare CJS call with no bundler: silently killed the entire script (zero log output at all, not even the native-log checkpoint before it) — bare `require()` has nothing to resolve against in the raw gadget engine.
4. Fix attempt 2, ran the script through **`frida-compile`** (a bundler for Frida agent scripts, conceptually the same role as webpack/esbuild but targeting Frida's JS engine) to properly inline `frida-java-bridge`. This got `Java` to resolve as a real object — but `typeof Java.perform` and `typeof Java.available` were still `undefined`. Cause: frida-compile's default bundle format is ESM, and `require()`'s CJS-interop shim doesn't correctly unwrap a bundled module's default export — you get back the wrapper, not the actual bridge API.
5. **Real fix**: use proper ES `import Java from 'frida-java-bridge';` syntax (not CJS `require()`) as the very first line of the script, matching frida-compile's native ESM bundling. Confirmed via logcat: `typeof Java.perform=function, typeof Java.available=boolean, Java.available=true` — then the whole hook fires correctly end to end.

## Status bar + nav bar cosmetic fixes (2026-09-01, later same session)

The reskin's dark background didn't extend into the Android status bar (stayed white) or leave room above the system navigation bar (bottom tab bar got overlapped). Root cause and fix, in order of what was actually tried:

1. **`window.setStatusBarColor()` is a documented no-op** on this build — confirmed via `adb shell dumpsys package com.myflame | grep targetSdk` → `targetSdk=36`. Android mandates edge-to-edge display (no opt-out) for apps targeting SDK 35+, and ignoring `setStatusBarColor`/`setNavigationBarColor` is a listed, intentional consequence — not a bug in the hook, not something Frida broke.
2. **Tried downgrading `targetSdkVersion`** (36 → 34, in `apktool.yml`'s `sdkInfo` block after a manual `apktool d`/edit/`apktool b` round-trip, then fed through the normal `objection patchapk` pipeline) to disable the edge-to-edge mandate and make the deprecated color API work again. **This made things worse** — produced a double-height white status bar strip, likely because the app's own native code already explicitly opts into edge-to-edge independent of `targetSdkVersion`, and downgrading the platform target while that native call still fires created an inconsistent state. **Reverted immediately** (`adb install -r` back to the saved-good APK) — do not repeat this approach.
3. **Real fix**: instead of fighting the deprecated color-setter API at all, paint a real opaque `android.view.View` directly into the `DecorView`, anchored to the top with height read from `WindowInsets.getInsets(WindowInsetsType.statusBars()).top` (with a `status_bar_height` resource-id fallback if that's 0). This isn't a system color API, so it isn't subject to the edge-to-edge deprecation — same technique modern edge-to-edge-aware apps use themselves. Implemented as `paintStatusBarOverlay()` in `hook.js`, called from the existing `onPageFinished` hook. Dedupes via `decorViewGroup.findViewWithTag(...)` so repeat `onPageFinished` calls (frontdoor.jsp + `/s/`) don't stack duplicate views. Kept `insetsController.setSystemBarsAppearance(0, 8)` for icon color (light icons on dark bg) since that API genuinely still works and isn't deprecated.
4. **Real Frida gotcha hit along the way**: a hook's method argument (here, the WebView `view` passed into `onPageFinished`) is only a valid wrapper for the *synchronous* duration of that hook call. Using it later inside `Java.scheduleOnMainThread()`'s async callback throws `Error: Wrapper is disposed; perhaps it was borrowed from a hook instead of calling Java.retain()...`. Fix: `var retainedView = Java.retain(view);` synchronously, before scheduling the async callback, then use `retainedView` inside it. (`recolorStatusBar`'s Activity-resolution path never hit this because `Java.cast()` produces an independently-referenced wrapper, not a borrowed one — only the raw hook-argument `view` itself needed retaining.)
5. **Bottom nav bar overlap** (system nav bar covering the reskin's own `.fr-nav` tab bar): same root cause (edge-to-edge, content extends under system bars) but a different fix, since this one wasn't a native color deprecation problem — the reskin needs actual *layout* padding equal to the nav bar's height, not a native color/view fix. `env(safe-area-inset-bottom)` isn't reliably populated by this WebView, so `hook.js`'s `pushNavBarInset()` measures the real inset natively (`WindowInsets.getInsets(WindowInsetsType.navigationBars()).bottom`, resource-id fallback `navigation_bar_height`) and pushes it into the page via `evaluateJavascript` as a CSS custom property (`--flame-navbar-inset`, converted from device px to CSS px via `window.devicePixelRatio`). `portal-reskin.user.js` defines that variable with an `env(safe-area-inset-bottom, 0px)` default (harmless 0 on desktop Tampermonkey, where this whole problem doesn't exist) and uses it in `.fr-nav`'s bottom padding + height and `.fr-content`'s bottom padding, all inside the existing `@media (max-width: 760px)` mobile block.
6. Also **halved `.fr-content`'s top padding** (24px → 12px, mobile only) per user feedback once the status bar was properly dark — the old value was tuned for a white status bar with no visual continuity; once the status bar matches the page background, less breathing room reads better.

**`apktool -J` flag syntax** (only needed when calling apktool directly, not through objection): the flag must come *immediately after* `apktool` and *before* the subcommand — `apktool -JXmx6g b <dir> -o <out>`, not `apktool b <dir> -o <out> -JXmx6g`. The wrapper script only strips consecutive `-J`-prefixed args from the very front of the argument list.

**`apktool build`'s incremental-change detection can silently ignore edits** — editing `apktool.yml` alone (without touching any file under `res/` or the manifest XML text itself) may print `AndroidManifest.xml and resources have not changed` and reuse a stale cached build artifact. Always pass `-f`/`--force` to `apktool b` after any manifest/yml edit, then verify with `aapt dump badging <apk> | grep targetSdkVersion` before trusting the output.
